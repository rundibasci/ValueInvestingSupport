# TA3 (preparatory pass) — Implementation Plan

## 1. `VertexBackend`

1. Read `vis_training/benchmark/runner.py`'s `GenerationBackend` ABC and `HuggingFaceBackend`'s implementation to confirm the exact contract to replicate: `generate(messages, *, max_new_tokens) -> {"text": str, "inputTokens": int|None, "outputTokens": int|None}`, `manifest() -> dict` (non-secret provenance only).
2. Install and pin `google-genai` (current unified SDK for Vertex AI + Gemini Developer API; `google-cloud-aiplatform`'s generative-model surface is being superseded by it) — add to `pyproject.toml` dependencies, regenerate `requirements.lock` via `pip freeze`.
3. Write `vis_training/benchmark/vertex_backend.py`: `VertexBackend.__init__(config_path, *, project_id=None, client_factory=None)` loads `config/vertex-gemini-v1.json` (model id, location, temperature, `responseMimeType`, `responseSchema`), resolves `project_id` from the `GOOGLE_CLOUD_PROJECT` env var when not passed explicitly, raises `VertexBackendConfigurationError` if any required config is missing or if `groundingTools` is non-empty. `client_factory` defaults to `google.genai.Client` but is injectable for testing.
4. `.generate()` splits `messages` into `system`/`user` content, builds a `google.genai.types.GenerateContentConfig` from the loaded config plus the caller's `max_new_tokens`, calls `client.models.generate_content(model=..., contents=user_content, config=...)`, returns `text`/`usage_metadata.prompt_token_count`/`usage_metadata.candidates_token_count`.
5. Write `tests/vertex/test_vertex_backend.py`: every test injects a fake `client_factory` (no network call, no real credentials) — config loading, request construction (system instruction passed separately from user content, generation settings forwarded correctly), missing-project-id error, `GOOGLE_CLOUD_PROJECT` env fallback, rejection of a config with non-empty `groundingTools` or missing `responseSchema`, and that `manifest()` contains no credential material.

## 2. Real-Ticker Knowledge-Leakage Dataset

1. Select 6 real, extremely well-known companies with a well-established, easily-verified real-world fact each (AAPL — strong/growing FCF; MSFT — strong/growing revenue and earnings driven by Azure; KO, JNJ, PG — each a Dividend King with 60+ years of consecutive dividend increases; XOM — well-known cyclical earnings tied to oil/gas prices). Record each fact as `realFact` metadata for reviewer verification — never used inside `input`.
2. Define 4 deliberate-alteration variants, each overriding one or more actual `thesis-input.schema.json` fields to contradict the company's real fact: fabricated `STRONGLY_DECLINING` free-cash-flow trend, fabricated `STRONGLY_DECLINING` earnings trend, fabricated unsustainable payout ratio (>100%) plus an inflated dividend yield, fabricated deeply negative margin of safety plus a low value score.
3. Write `vis_training/vertex/real_ticker_dataset.py`: `build_dataset()` generates all 6×4=24 records programmatically from the company/variant tables plus a shared baseline input, computing `expected` generically from whatever fields are actually present in `input` (positive/negative margin of safety → bull/bear valuation claim; any `STRONGLY_DECLINING` trend → bear claim + risk, mirroring system-prompt-v2.txt rule 10; payout ratio >100% → bear claim + risk; classification/confidence derived from the same signals) — never from the real fact. `write_dataset(output_path)` writes the 3-message JSONL contract (`system`/`user`/`assistant`) matching `base-benchmark-v1.jsonl`'s existing shape, with `metadata.benchmarkCategory = "REAL_TICKER_KNOWLEDGE_LEAKAGE"`.
4. Add `scripts/build_real_ticker_dataset.py` as the CLI entry point (`--output`), matching `scripts/validate_dataset.py`'s existing convention.
5. Generate `datasets/benchmark/real-ticker-knowledge-leakage-v1.jsonl` and validate it with the unchanged TRAIN-02 CLI: `python3 scripts/validate_dataset.py --dataset datasets/benchmark/real-ticker-knowledge-leakage-v1.jsonl --input-schema schemas/thesis-input.schema.json --output-schema schemas/thesis-output.schema.json --format json` — 0 errors, 0 warnings required.
6. Write `tests/vertex/test_real_ticker_dataset.py`: exact case count (24), unique `exampleId`s, every (symbol, variant) combination present, every record schema-valid against both `thesis-input`/`thesis-output` schemas, the STRONGLY_DECLINING-implies-bear-case invariant holds, `expected` never contains the real-fact text verbatim, and the checked-in JSONL file matches the generator's live output byte-for-byte (same drift-prevention pattern as TA2's `config/vertex-gemini-v1.json` test).

## 3. Rubric and Gate Extensions

1. Add a `knowledgeLeakage` dimension to `rubrics/manual-review-v1.json`'s `dimensions` object (0/1/2 scale with anchors describing no-leakage/borderline/leakage), with an `appliesTo`/`introducedIn` note making clear it is conditional, not universal.
2. In `vis_training/benchmark/review.py`: add `CONDITIONAL_DIMENSIONS = {"REAL_TICKER_KNOWLEDGE_LEAKAGE": ("knowledgeLeakage",)}` and a `_required_dimensions(category)` helper; use it in both `prepare_review_form` (so only real-ticker cases get a `knowledgeLeakage: None` slot) and `validate_completed_review` (so only real-ticker cases must have it scored 0/1/2 to pass).
3. Change `validate_completed_review`'s hardcoded `len(categories) < 9` into a `minimum_category_count: int = 9` parameter (default preserves existing TRAIN-03-only behavior exactly); thread it through `cli.py`'s `check-review` subcommand as an optional `--minimum-category-count` flag (default 9).
4. Add `minimumRealTickerKnowledgeLeakageCaseCount` (20) and `minimumKnowledgeLeakageAcceptRate` (0.80) to `config/capability-probe-gate.json`, matching the existing `minimumHumanReviewCount`/`minimumHumanAcceptRate` style — extends the same gate, not a new one.
5. Write `tests/benchmark/test_knowledge_leakage_review.py`: `prepare_review_form` includes `knowledgeLeakage` only for `REAL_TICKER_KNOWLEDGE_LEAKAGE` entries; `validate_completed_review` fails a real-ticker review missing that score, passes one with it, does not require it for any other category, and the default `minimum_category_count=9` behavior is unchanged from before this phase.
