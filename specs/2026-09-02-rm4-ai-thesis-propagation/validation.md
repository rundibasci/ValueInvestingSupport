5. **[live, bug found]** The `netDebtToEbitda:35.40` value for `O` was immediately suspicious — RM2/RM3's own live-verified figure for `O` is ~9.1×. Cross-checked against `fundamental_snapshot`'s real persisted columns (`total_debt`, `cash`, `ebitda` for the TTM row: `32,853,271,000 − 434,842,000 = 32,418,429,000` net debt; `ebitda = 3,550,842,000`; `32,418,429,000 / 3,550,842,000 = 9.13`, matching RM2 almost exactly). Root cause: `deriveNetDebtToEbitda` read `ebitdaHistory.get(ebitdaHistory.size() - 1)` as "latest" — but `FmpAdapter.toFundamentalSnapshot` builds every `*History` list in FMP's own **newest-first** order (`income.get(0)`/`balance.get(0)` are read as the TTM/current values elsewhere in that same method), and `SeedTickerService.persistFundamentals` only falls back to the domain record's scalar `totalDebt()`/`cash()` at `i == 0` — both independently confirm index 0, not the last index, is "latest". The `size()-1` indexing was inherited unchanged from the pre-RM4 `operatingIncomeHistory`-based version of this method (same bug, pre-existing, never previously live-verified against a multi-year real dataset). **Fixed**: `ebitdaHistory.get(0)` instead of `.get(size() - 1)`, with the reasoning recorded in the method's own Javadoc. The corresponding unit test was rewritten to use index-0-correct fixture data (index-0 values distinct from index-1, so the test fails if either the wrong field or the wrong index is read).

## Corrections Made During Implementation (honest account)

Per this project's own "verify against real code, not spec text" discipline (RM2/RM3/TA4/TA5 precedent):

1. **A real, pre-existing indexing bug was found and fixed via this phase's own live smoke test** (Manual Verification steps 5-6): `deriveNetDebtToEbitda` read the *oldest* year in a multi-year history as "latest" (`.get(size() - 1)` on a newest-first array), inherited unchanged from the pre-RM4 `operatingIncomeHistory`-based version of this exact method. This is not a regression introduced by RM4's own field rename — it is a bug RM4's own "switch to a precise, real EBITDA figure" goal newly exposed to live verification for the first time, and it was caught, root-caused against real persisted `fundamental_snapshot` columns, fixed, and re-verified live before this phase's own merge, per this project's "the test did its job, don't leave a caught bug in" precedent (RM3's own validation.md, Correction 2).
2. **A related, larger-scope bug was found but deliberately NOT fixed here, and is flagged below as a known risk**: `ThesisInputBuilder.classifyTrend`'s existing (pre-RM4, TA4-authored) trend logic assumes the *opposite* array direction from what `deriveNetDebtToEbitda` (and `FmpAdapter`/`SeedTickerService`) actually use — it iterates history forward and treats the *last* period-over-period change as "latest," which, against the confirmed newest-first array convention, actually reflects the *oldest* comparable period in the window, not the most recent. This plausibly means `revenueTrend`/`earningsTrend`/`freeCashFlowTrend` have been computed in reverse-chronological order in every AI thesis generated since TA4 shipped (2026-08-28). **Deliberately not fixed in this phase**: RM4's own scope (`requirements.md`) is the REIT-field propagation and the `netDebtToEbitda` source fix specifically; `classifyTrend`'s ordering affects three fields used by every thesis regardless of sector, has a much larger blast radius, and deserves its own dedicated investigation/spec with real multi-year verification across several tickers — not a same-session scope expansion bundled into RM4 on top of an already-found fix. See Known Risks below; flagged for a prompt follow-up phase.
3. **The two checked-in `vis-model-training` benchmark datasets** (`datasets/benchmark/real-ticker-knowledge-leakage-v1.jsonl`, `datasets/benchmark/scenarios-benchmark-v1.jsonl`) embed the live prompt text verbatim in `messages[0].content` and went stale the moment `system-prompt-v3.txt` changed — caught by `test_checked_in_dataset_matches_generator_output`/`test_checked_in_dataset_matches_live_converter_output` failing, not by inspection. Regenerated via each module's own `write_dataset()` function (the same "regenerate via the real derivation, don't hand-edit" discipline as `config/vertex-gemini-v1.json`), not anticipated in `plan.md` (which only named the schema/config/fixture files) but a direct, mechanical consequence of the prompt edit Group 4 already called for.

## Known Risks (carried forward or introduced by this phase)

- **`classifyTrend`'s array-direction assumption is plausibly inverted for every AI thesis generated since TA4 (2026-08-28)** — found in Correction 2 above, **not fixed in this phase** (out of RM4's own stated scope, larger blast radius, needs dedicated investigation). This means `revenueTrend`/`earningsTrend`/`freeCashFlowTrend` may have been reading the *oldest* comparable period in a multi-year window as "latest" for every security, every sector, since the AI Thesis feature shipped — a real correctness concern for a feature whose entire value proposition is "reason from evidence, don't invent." Strongly recommended as the next phase after RM4, verified against real multi-year data for several tickers (not just synthetic 2-element test fixtures, which cannot expose a direction bug). Flagged here rather than left for a future reader to rediscover independently.
- **`netDebtToEbitda`'s two independent derivations (`ThesisInputBuilder`'s direct `netDebt` read vs. RM2's `totalDebt − cash`) can still produce visibly different numbers for the same REIT** — confirmed live for `O`: `9.13` (thesis input, post-fix) is close to but not identical to RM2/RM3's own live-verified `~9.1298` (`SectorMetricResponse`), a small residual gap from the two independently-computed net-debt figures (Decision 3, accepted, not unified in this phase).
- **No automated check exists for prompt wording quality** — the new REIT-awareness rule's effectiveness is judged by two manually-read live responses, not a benchmark suite. A future TRAIN-03/04-style evaluation pass could close this gap.
- **Historical `InvestmentThesisResult` rows generated before this phase keep their old, incorrectly-indexed `operatingIncomeHistory`-approximated `netDebtToEbitda`** — only new generations after merge see the corrected value. Not a backfill target this phase.
