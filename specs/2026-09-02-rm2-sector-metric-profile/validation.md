## Corrections Made During Implementation (honest account)

Per this project's own "verify against real code/live data, not spec text" discipline (TA4/TA5/RM1 precedent), several things in `plan.md`'s original sketch turned out different once actually checked:

1. **`interestExpense` is confirmed live, not left `INSUFFICIENT_DATA`.** `plan.md`'s original contingency assumed EBITDA interest coverage might ship unavailable, matching RM1's posture toward NOI. Live confirmation against FMP Premium's real `/income-statement` payload for `O`, `PLD`, and `SPG` (via `curl` against the FMP API directly, this session, real API key) found `interestExpense` present and non-null on all three (`O`: 1,142,201,000; `PLD`: 1,002,593,000; `SPG`: 974,836,000). Wired it in fully: `FmpIncomeStatementEntry.interestExpense`, `FundamentalSnapshot.interestExpenseHistory`/`.interestExpense`, `SectorMetricService.interestCoverageEbitda()`, and a new `fundamental_snapshot.interest_expense` column in `V29`.
2. **The Quality pillar's REIT formula reads from `FundamentalSnapshot`, not `RatioSnapshot`.** The first implementation attempt tried computing FFO margin from `RatioSnapshot.getFfoPerShare()` (a TTM per-share figure) against `FundamentalSnapshot`'s ANNUAL revenue — a period mismatch, and `RatioSnapshot` has no revenue field to pair cleanly anyway. Corrected to compute directly from the same ANNUAL `FundamentalSnapshot` row: `(netIncome + D&A) / revenue`, same period throughout, no per-share conversion needed.
3. **`ValueScoreService`'s REIT MoS pillar calls `ValuationHistoryService.compute()` live**, not via a persisted `ValuationBandResult` lookup, once it became clear during implementation that `ValuationHistoryService.compute()` is itself only ever called on-demand elsewhere in this codebase (`MoatController`, `SecurityReviewService`) — there is no ingestion-time job that populates `valuation_band_result`. A lookup-only approach would have found no `"P_FFO"` row at all for a REIT's very first score computation after seeding. `plan.md`'s Group 7.2 sketch assumed a repository lookup; the actual implementation calls `valuationHistoryService.compute(security)` directly and reads the `P_FFO` entry from its returned list.
4. **`PipelineRunService` needed no separate ordering fix**, contrary to `plan.md` Group 5.2's assumption that it might. Investigation (per that same group's own instruction to confirm before assuming) found `PipelineRunService.run()` delegates seeding entirely to `SeedService.seedTickers()` → `SeedTickerService.seedOne()`, so Decision 3's `SeedTickerService` fix already covers `PipelineRunService`'s own (redundant) second `valueScoreService.compute()` call.
5. **`FundamentalSnapshot.capitalExpenditureHistory` is ingested but not read by `SectorMetricService`.** AFFO's recurring-capex figure reuses the existing `maintenanceCapexDepreciationRatio` config value applied to D&A (`OwnerEarningsCalculator.estimateMaintenanceCapex`), per the definition doc's explicit "reuse the existing config value" instruction (§4.2) — not a split of total capex as one reading of the doc's §3 data-gap table could suggest. `capitalExpenditure` is still ingested (mechanical, low-risk, already-confirmed provider field) for potential future cross-check/display use, but is currently unused by any formula.

## Known Risks (carried forward or introduced by this phase)

- **AFFO's D&A × 0.70 recurring-capex heuristic materially understates AFFO for net-lease REITs** — confirmed twice with real `O` data: the original hand-computed check (~$1.99 vs. ~$4.22 company-reported) and, in the live end-to-end verification, the persisted `affo_per_share = 1.9897` for `O`. Every AFFO-derived figure (AFFO payout ratio, the Dividend pillar, P/AFFO) inherits this understatement. A REIT-specific recurring-capex heuristic (rather than reusing the generic DCF owner-earnings ratio) is a natural next recalibration target, not attempted in this phase to avoid inventing an unvalidated new assumption under time pressure.
- **Net Debt/EBITDA (raw, unadjusted `ebitda`) reads more conservatively than a REIT's own company-reported EBITDAre-based leverage** — confirmed twice: the original hand-computed check (~9.1× vs. ~5.5×) and the live-persisted `net_debt_to_ebitda = 9.1298` for `O`, which live-tested `O`'s `safetyScore` down to `0.0` (crossing the 8.0 "high" threshold). The Safety pillar's first-pass thresholds (`SectorMetricProperties`) currently under-score a conservatively-levered, investment-grade REIT like `O` — directly caused by RM1's confirmed, unavoidable absence of a gains/losses-on-sale adjustment field in FMP's data, not something RM2 can fix without a different data source. This is the single highest-value target for a future recalibration pass, since it is now evidenced against a live-observed score outcome, not just a formula spot-check.
- **The Safety pillar's interest-coverage bonus is withheld whenever the base leverage tier is 0**, even if interest coverage alone is strong — observed live for `O` (interest coverage 3.11× clears the 3.0 bonus threshold, but `netDebtToEbitda` 9.13× already zeroed the base, so no bonus applies). This mirrors the existing GAAP-branch bonus-guard pattern (`base.compareTo(ZERO) > 0`) exactly and is confirmed intentional, not a bug — flagged here only because it is a real, now-observed behavior worth knowing about when reading a REIT's Safety sub-score.
- **Quality-pillar formula (FFO margin) and Safety/Dividend thresholds remain first-pass calibrations** (`requirements.md` Decisions 6–7), now with real-data findings from both a hand-computed check and a live end-to-end run motivating a future recalibration pass, rather than a purely theoretical caveat.
- **`SectorMetricService` is seed/pipeline-time-only, not nightly-scheduled** (`requirements.md` Decision 2) — a REIT security's sector metrics go as stale between seeds as its moat/capital-allocation data already does.
- **`ValueScoreService.computeMosScoreReit` triggers a `ValuationHistoryService.compute()` delete-and-reinsert of all five `ValuationBandResult` rows on every REIT score computation** — consistent with that method's existing on-demand-recompute design used elsewhere, but RM2 adds a third caller. Not a correctness issue.
- **REIT MoS is a relative-valuation signal (P/FFO percentile), not an intrinsic-value margin of safety** — RM3's security-detail surfacing and RM4's AI-thesis propagation must carry this distinction forward explicitly (`requirements.md` Decision 8).
