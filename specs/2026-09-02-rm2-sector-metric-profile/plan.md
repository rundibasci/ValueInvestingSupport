## 4. `SectorMetricService` — the computation engine

New class `backend/src/main/java/it/mazzoni/vis/scoring/SectorMetricService.java`, same package as `ValueScoreService` (tightly coupled to scoring, per `specs/sector-aware-valuation-metrics.md` §2), mirroring `MoatAssessmentService`'s `analyze(Security)`/`analyze(String)` two-overload shape ([backend/src/main/java/it/mazzoni/vis/moat/MoatAssessmentService.java:50-59](backend/src/main/java/it/mazzoni/vis/moat/MoatAssessmentService.java#L50)).

1. `public void compute(String symbol)` → resolves `Security`, delegates to `compute(Security)` (`SymbolNotFoundException` on miss, matching every other `*Service.compute(String)` entry point in this codebase).
2. `public void compute(Security security)`:
   - No-op immediately (return) unless `SectorClassifier.isReit(security.getSector())` — every non-REIT security is untouched, per the additive requirement.
   - Load all persisted `RatioSnapshot` rows for the security (`ratioSnapshotRepository.findBySecurity(security)`), both `ANNUAL` and `TTM`.
   - For each `RatioSnapshot` row, find the matching `FundamentalSnapshot` by `(security, period, reportDate)` — add `FundamentalSnapshotRepository.findBySecurityAndPeriodAndReportDate(Security, Period, LocalDate)` (a new derived-name method; `RatioSnapshot`/`FundamentalSnapshot` rows for the same period share `reportDate` by construction in both `SeedTickerService.persistFundamentals`/`persistRatioSnapshot` and `BulkFundamentalsSyncJob`/`BulkRatiosSyncJob` — confirm this holds for both ingestion paths before relying on it, and fall back to `Optional.empty()` — not an exception — if no match is found for a given row, since a missing pairing means `INSUFFICIENT_DATA` for that row, not a hard failure).
   - If no matching `FundamentalSnapshot`, or its `depreciationAndAmortization`/`netIncome`/`sharesOutstanding` are null, leave that row's seven new fields `null` and continue to the next row (never throw, never fabricate — Design Principle 12).
   - **FFO per share**: `(netIncome + depreciationAndAmortization) / sharesOutstanding` — the D&A-only NAREIT approximation `specs/sector-aware-valuation-metrics.md` §3/§4.1 documents (gains/losses/impairment add-backs out of scope, confirmed unavailable in RM1).
   - **AFFO per share**: `ffoPerShare − (recurringCapexPerShare)`, where `recurringCapexPerShare = (|capitalExpenditure| × maintenanceCapexRatio) / sharesOutstanding`. `capitalExpenditure` is not currently on `FundamentalSnapshot` — check `FmpCashFlowEntry`/`FmpAdapter` for whether it is already captured anywhere reachable from `FundamentalSnapshot`; if not, this is a second, smaller RM1-style gap to close in this group (add `capitalExpenditureHistory` the same way RM1 added `depreciationAndAmortizationHistory`) — confirm before writing the formula, do not assume the field exists. `maintenanceCapexRatio` reuses `valuation.enhancements.maintenance-capex-depreciation-ratio` (0.70, [application.yml:98](backend/src/main/resources/application.yml#L98)) via the existing `ValuationEnhancementsProperties`-equivalent binding — do not duplicate the constant into a new property.
   - **Implied price for this row**: TTM row → most recent `PriceQuote.getClose()` (`priceQuoteRepository.findTopBySecurityOrderByQuoteDateDesc`, matching `SeedTickerService.currentPrice`'s exact pattern, [SeedTickerService.java:138-141](backend/src/main/java/it/mazzoni/vis/admin/SeedTickerService.java#L138)). ANNUAL rows → **derive** the historical price from the row's own provider-supplied `peRatio` and the paired `FundamentalSnapshot.eps`: `impliedPrice = peRatio × eps` — this platform does not ingest a dense historical daily-price archive (`QuoteRefresh` only refreshes current watchlist/holding prices every 15 min, per `specs/roadmap.md` → B3), so deriving price from the provider's own point-in-time P/E is the only grounded source for a multi-year P/FFO band; document this derivation in a class-level Javadoc comment, not just in this spec. Both `peRatio` and `eps` null/zero/negative → leave `priceToFfo`/`priceToAffo` null for that row.
   - **P/FFO, P/AFFO**: `impliedPrice / ffoPerShare` (respectively `affoPerShare`) — null if either operand is null, zero, or non-positive.
   - **Net Debt/EBITDA**: `(totalDebt − cash) / ebitda`, reading `totalDebt`/`cash`/`ebitda` off the same paired `FundamentalSnapshot` row (all three already present since RM1 for `ebitda`, earlier for `totalDebt`/`cash`) — null if `ebitda` is null or ≤ 0.
   - **EBITDA interest coverage**: `ebitda / interestExpense`. `interestExpense` is not currently on `FundamentalSnapshot` — check `FmpIncomeStatementEntry`/`FmpAdapter` for availability the same way the AFFO capex check does; if absent, this field stays `INSUFFICIENT_DATA` (null) for RM2 and is recorded as an open item in `validation.md`, mirroring how RM1 scoped out NOI rather than guessing.
   - **AFFO payout ratio**: `dividendPerShare / affoPerShare`, where `dividendPerShare = ratio.getPayoutRatio() × fundamental.getEps()` — the same implied-value technique as the price derivation above, reusing the provider-supplied GAAP payout ratio rather than adding a new dividends-paid ingestion field. Null if `payoutRatio`, `eps`, or `affoPerShare` is null, or `affoPerShare` ≤ 0.
   - Set all seven fields on the `RatioSnapshot` entity and save (`ratioSnapshotRepository.save(row)` per row, or `saveAll` — match whichever style `MoatAssessmentService`/`CapitalAllocationService` use for their own row updates).
3. Test `SectorMetricServiceTest` (unit, mocked repositories, mirroring `ValueScoreServiceTest`'s Mockito style):
   - Non-REIT security (`sector = "Technology"`) → `compute()` is a no-op, no repository writes.
   - REIT security, TTM row with a full paired `FundamentalSnapshot` and a `PriceQuote` → asserts the exact FFO/AFFO/P-FFO/P-AFFO/NetDebtEbitda/AffoPayout values for a known hand-computed input set (same "known inputs, hand-verified expected output" style as `ValueScoreServiceTest::compute_knownInputs_allSubscoresCorrect`).
   - REIT security, ANNUAL row with `peRatio`+`eps` present but no `PriceQuote` for that date → confirms the implied-price derivation is used (not `null`) and matches `peRatio × eps`.
   - REIT security, row with no matching `FundamentalSnapshot` → all seven fields stay `null`, no exception.
   - REIT security, `ebitda` present but ≤ 0 → `netDebtToEbitda`/`interestCoverageEbitda` stay `null` (never a nonsensical or negative-denominator ratio surfaced).

## 5. Wiring into ingestion — fix the ordering gap before `ValueScoreService.compute()` reads it

`SeedTickerService.seedOne()` currently calls `valueScoreService.compute(symbol)` ([SeedTickerService.java:123](backend/src/main/java/it/mazzoni/vis/admin/SeedTickerService.java#L123)) **before** `recomputeDerivedAnalytics` ([SeedTickerService.java:124](backend/src/main/java/it/mazzoni/vis/admin/SeedTickerService.java#L124)), where `moatAssessmentService.analyze`/`capitalAllocationService.analyze` currently live. Placing the new `sectorMetricService.compute(security)` call inside `recomputeDerivedAnalytics` would mean a freshly-seeded REIT's very first `ValueScore` (the one returned in the seed API response) is computed against `null` FFO/AFFO fields — silently wrong on first seed, self-correcting only on the next `GET /score` call (which recomputes live via `ScoreService.getScore` → `valueScoreService.compute`, confirmed at [ScoreService.java:42](backend/src/main/java/it/mazzoni/vis/scoring/ScoreService.java#L42)). This is a real, non-obvious ordering bug to avoid, not a hypothetical.

1. Call `sectorMetricService.compute(security)` in `SeedTickerService.seedOne()` **after** `persistPriceQuote(security, symbol)` (line 105 area — price must exist for the TTM row's implied price) and **before** `valueScoreService.compute(symbol)` (line 123) — i.e., insert it alongside `enrichDerivedProfileData(security)`/`persistDividends`/`persistInsiderTrades`, not inside `recomputeDerivedAnalytics`.
2. Apply the identical fix to `PipelineRunService` ([backend/src/main/java/it/mazzoni/vis/pipeline/PipelineRunService.java:41](backend/src/main/java/it/mazzoni/vis/pipeline/PipelineRunService.java#L41)) — confirm its own price/ratio ingestion ordering first (read the class before assuming it matches `SeedTickerService`'s structure) and insert `sectorMetricService.compute(security)` at the equivalent point, before its own `valueScoreService.compute(...)` call.
3. Do **not** wire `SectorMetricService` into the nightly `BulkRatiosSyncJob`/`BulkFundamentalsSyncJob` jobs in this phase — `MoatAssessmentService`/`CapitalAllocationService`/`RiskAnalysisService` are already seed-time-only in this codebase (confirmed: no `@Scheduled` caller exists for any of them), and `ScoreService.getScore` recomputes `ValueScore` live on every read regardless, so a REIT's sector metrics go stale only exactly as much as moat/capital-allocation data already does between seeds. Expanding nightly-job scope is out of scope for RM2 (see `requirements.md` → Out of Scope) — note it is an existing platform limitation, not one RM2 introduces.
4. Test: extend `SeedTickerServiceTest`/`PipelineRunServiceTest` (whichever exists) with a REIT-sector fixture asserting `sectorMetricService.compute` is invoked before `valueScoreService.compute` for that symbol (an ordering assertion via `Mockito.inOrder`, not just a "was called" check — the ordering is the actual bug being fixed).

## 7. `ValueScoreService` — REIT branch for all five pillars

`ValueScoreService.compute()` ([backend/src/main/java/it/mazzoni/vis/scoring/ValueScoreService.java:56-106](backend/src/main/java/it/mazzoni/vis/scoring/ValueScoreService.java#L56)) resolves `weightProfileKey` (unchanged — still `SectorClassifier.isReitOrUtility`-gated, still picks the `"reit-utility"` weight tuple) and now, separately, whether `SectorClassifier.isReit(security.getSector())` — the **metric-source** branch — gating each `computeXScore` call, matching `specs/sector-aware-valuation-metrics.md` §2's two-layer design (weight profile unchanged; metric source new).

1. Inject `SectorMetricProperties` (Group 8) and `ValuationBandResultRepository` into `ValueScoreService`'s constructor (update every existing test/mock construction site — `ValueScoreServiceTest` at minimum).
2. `computeMosScore` — add `computeMosScoreReit(Security security)` overload: look up the `P_FFO` `ValuationBandResult` for this security (`valuationBandResultRepository.findBySecurityAndResultDateOrderByMetricAsc`, filter `metric.equals("P_FFO")`, most recent `resultDate`); if absent or `INSUFFICIENT_DATA`, return `BigDecimal.ZERO` (same null-safety posture as every other pillar). Otherwise map `currentPercentile` to the pillar's 0–30 scale using **percentile bands, not raw MoS-percentage bands** (the REIT MoS signal is relative-valuation, not a computed intrinsic-value gap): `≤25th percentile → 30`, `≤50th → 20`, `≤75th → 10`, `>75th → 0` — mirrors the existing `computeMosScore`'s four-tier shape while being honest that this is a different signal (cheap-vs-own-history, not cheap-vs-intrinsic-value); document this distinction in the method Javadoc, and again in `requirements.md` → Decisions, since it's a real behavioral difference the AI thesis / UI must not blur (RM3/RM4 concern, flagged here for continuity).
   - Call `compute()` with a branch at the top: `if (SectorClassifier.isReit(security.getSector())) { mosScore = computeMosScoreReit(security); } else { mosScore = computeMosScore(valuation); }`.
3. `computeQualityScore` — add `computeQualityScoreReit(RatioSnapshot ratio, FundamentalSnapshot latestAnnual)` using **FFO margin** (`ffoPerShare × sharesOutstanding / revenue`, i.e. FFO ÷ revenue) as the quality signal — the closest self-consistent reading of the source doc's illustrative `QUALITY_FFO_MARGIN` name (`specs/sector-aware-valuation-metrics.md` §2's pseudocode names it but §4 does not define a formula for it — this is this phase's own explicit calibration, documented as such in `requirements.md`, not a value already agreed upon elsewhere). Thresholds: mirror the existing ROIC/ROE bands' *shape* (three tiers + zero) but recalibrated for FFO margin, which typically runs far higher than ROIC (`≥50% → 25`, `≥35% → 18`, `≥20% → 10`, `else 0`) — a first-pass calibration to revisit once real REIT FFO-margin distributions are observed (same posture as Group 9's leverage-threshold note below), not sourced from a specific published benchmark.
4. `computeSafetyScore` — add `computeSafetyScoreReit(RatioSnapshot ratio)` using `netDebtToEbitda`/`interestCoverageEbitda` in place of `debtToEquity`/`currentRatio`: base tiers `≤5.5× → 20`, `≤6.5× → 14`, `≤8.0× → 7`, `else 0`; `+2` bonus (capped at 20) if `interestCoverageEbitda ≥ 3.0×`, mirroring the existing `currentRatio ≥ 2.0` bonus structure exactly. **These thresholds are a first-pass calibration** (`specs/sector-aware-valuation-metrics.md` §10 open question 3 explicitly defers exact NAREIT/sector benchmark sourcing to RM2 "not guessing here" — this plan makes the calibration call so RM2 ships, documents it plainly as provisional, and does not claim it is sourced from a specific published dataset).
5. `computeGrowthScore` — add `computeGrowthScoreReit(List<FundamentalSnapshot> annuals, List<RatioSnapshot> reitAnnualRatios)` using FFO-per-share YoY growth: pair the two latest ANNUAL `RatioSnapshot` rows' `ffoPerShare` values the same way `computeGrowthScore` already pairs `annuals.get(0)`/`annuals.get(1)` revenue — needs the ANNUAL `RatioSnapshot` list threaded into `compute()` alongside the existing `annuals` (`FundamentalSnapshot`) list; same 0.10/0.05/0.0 thresholds as the existing method (no sector-specific growth-threshold guidance exists in the source doc, so the existing bands are reused verbatim, not recalibrated).
6. `computeDividendScore` — add `computeDividendScoreReit(RatioSnapshot ratio)` using `affoPayoutRatio` in place of the yield+streak combination: `≤85% → 10`, `≤100% → 7`, `≤115% → 4`, `else 0` (or `null` payout → `0`) — again a first-pass calibration, documented as such, replacing rather than supplementing the existing yield/streak logic since `specs/sector-aware-valuation-metrics.md` frames AFFO payout ratio as *the* sustainability check for this sector, not one input among several.
7. Every branch above falls through to the existing formula verbatim when `SectorClassifier.isReit(...)` is `false` — **zero behavioral change for `financial`/`cyclical`/`dividend-paying`/`non-dividend-growth`**, confirmed by running the full existing `ValueScoreServiceTest` suite unmodified except for the constructor-signature update in Group 7.1.

Tests: `ValueScoreServiceTest` gains one REIT-branch test per pillar (five new tests, hand-computed expected values, same style as the existing `compute_knownInputs_allSubscoresCorrect`) plus one full `compute_reitSecurity_allFivePillarsUseReitMetrics` end-to-end test; every pre-existing test in the class must still pass unmodified in its assertions (only the constructor call site changes).
