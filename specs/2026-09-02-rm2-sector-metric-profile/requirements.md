# RM2 — SectorMetricProfile & REIT Metric Computation

## Context

RM0 (`4ca4ab3`, merged as PR #9, 2026-09-01) extracted `SectorClassifier` and shipped an interim GAAP-metric caveat for REIT/real-estate/utility securities. RM1 (`7f7a789`, merged 2026-09-01) confirmed live against FMP Premium (`O`, `PLD`, `SPG`) that `depreciationAndAmortization` and a precise `ebitda` are both present on `/income-statement`, added them to `FundamentalSnapshot`, and resolved the NOI-availability open question: NOI is confirmed absent from every FMP endpoint checked, so Implied Cap Rate and NAV per share are out of scope (`specs/sector-aware-valuation-metrics.md` §5, Fallback C). Neither RM0 nor RM1 has a `specs/` spec directory — both were implemented directly against the definition doc and merged same-day; this phase is the first RM-group phase planned through the normal spec workflow, and treats RM0/RM1's actual merged code (not just the definition doc's prose) as ground truth throughout.

RM2 is the metric-computation phase: it builds the `SectorMetricProfile` branch point `specs/sector-aware-valuation-metrics.md` §2 defines, computes FFO/AFFO/P-FFO/P-AFFO/Net-Debt-EBITDA/EBITDA-interest-coverage/AFFO-payout-ratio for REIT-classified securities, persists them on `RatioSnapshot`, and wires `ValueScoreService`'s five pillars to consume them for the REIT metric-source key — while leaving every non-REIT sector's scoring formulas byte-for-byte unchanged. Screener/security-detail surfacing (RM3) and AI-thesis propagation (RM4) are separate, later phases that consume what RM2 persists.

The source-of-truth definition doc, `specs/sector-aware-valuation-metrics.md`, contains most of RM2's formulas and architecture already (§2, §4, §7) but explicitly defers several calibration decisions to "RM2, not guessing here" (§10, open questions 3–4) and leaves the Quality-pillar formula named but undefined (§2's illustrative `QUALITY_FFO_MARGIN` has no corresponding formula in §4). This phase makes those calls explicitly (see Decisions below) rather than blocking on further research — consistent with how RM1 made its own NOI-fallback call rather than leaving it open indefinitely.

## Decisions

1. **`SectorClassifier.isReit` is a new, separate method from `isReitOrUtility`.** The weight-profile layer (existing `"reit-utility"` key, unchanged) and the metric-source layer (new, REIT-only) are deliberately different classifications — a utility security keeps its GAAP metrics (Debt/Equity, ROE, EPS payout) under the REIT-utility *weight* profile, per `specs/sector-aware-valuation-metrics.md` §10 open question 4, which this phase resolves for the metric layer without touching the weight layer.
2. **Sector metrics are computed at seed/pipeline time, not via a new nightly job.** `MoatAssessmentService`, `CapitalAllocationService`, and `RiskAnalysisService` are already seed-time-only in this codebase (no `@Scheduled` caller exists for any of them); `SectorMetricService` follows the same precedent rather than expanding nightly-job scope. `ScoreService.getScore` recomputes `ValueScore` live on every read (confirmed at `ScoreService.java:42`), so staleness between seeds is bounded the same way moat/capital-allocation data already is — an existing platform characteristic, not a new gap RM2 introduces.
3. **`SectorMetricService.compute()` must run before `ValueScoreService.compute()` in both `SeedTickerService.seedOne()` and `PipelineRunService`**, not inside `recomputeDerivedAnalytics` (where `MoatAssessmentService`/`CapitalAllocationService` currently live). Found by reading the actual call order in `SeedTickerService.seedOne()`: `valueScoreService.compute(symbol)` runs *before* `recomputeDerivedAnalytics`, so placing the new call there would make a freshly-seeded REIT's first `ValueScore` silently wrong (computed against `null` FFO/AFFO) until the next `GET /score` call recomputes live. This is a real ordering bug this plan avoids, not a stylistic preference.
4. **Historical (ANNUAL) implied price is derived as `peRatio × eps`, not sourced from a historical price archive.** This platform does not ingest dense historical daily prices — `QuoteRefreshJob` only refreshes current watchlist/holding prices every 15 minutes (`specs/roadmap.md` → B3) — so there is no historical price series to pair with each ANNUAL `RatioSnapshot` row for a multi-year P/FFO band. The provider's own `peRatio` for that historical period, combined with the paired `FundamentalSnapshot.eps`, is the only grounded source available without a new ingestion dependency. The current (TTM) row instead uses the actual latest `PriceQuote.getClose()`. Both derivations are documented in `SectorMetricService`'s Javadoc so a future reader does not mistake the ANNUAL figures for observed prices.
5. **AFFO payout ratio's `dividendPerShare` is derived as `payoutRatio × eps`**, the same implied-value technique as Decision 4, rather than adding a new dividends-paid ingestion field. `DividendRecord` exists for streak/CAGR tracking but not as a clean trailing-twelve-month per-share cash figure aligned to each `RatioSnapshot` row's period; reusing the provider-supplied GAAP payout ratio avoids a second new ingestion dependency for a single derived ratio.
6. **The Quality pillar's REIT formula (FFO margin = FFO ÷ Revenue) is this phase's own calibration**, not a value already settled elsewhere. `specs/sector-aware-valuation-metrics.md` §2's illustrative pseudocode names `QUALITY_FFO_MARGIN` but §4 (which defines every other REIT formula precisely) has no corresponding section — this is a gap in the source doc, not an oversight in reading it. FFO margin is the most direct "how much of revenue converts to distributable cash earnings" analogue to the existing ROIC/ROE-based quality signal, and is flagged here explicitly so it can be revisited if the definition doc is ever updated with a different intended formula.
7. **Safety and Dividend pillar thresholds (Net Debt/EBITDA bands, interest-coverage bonus, AFFO payout bands) are first-pass calibrations**, per `specs/sector-aware-valuation-metrics.md` §10 open question 3's explicit instruction ("propose sourcing from public NAREIT/sector benchmark data during RM2, not guessing here" — interpreted as "RM2 must make an initial, documented call, not that RM2 is blocked pending external benchmark sourcing that has no defined source or owner"). All thresholds live in `SectorMetricProperties`/`application.yml`, not hardcoded, so recalibration against real NAREIT data later is a config change, not a code change.
8. **The REIT MoS pillar is a relative-valuation signal (P/FFO percentile vs. own history), not an intrinsic-value gap** — a structurally different signal from every other sector's `composite fair value vs. price` MoS. This is called out explicitly (in `plan.md` Group 7.2 and here) because RM3's security-detail surfacing and RM4's AI-thesis propagation must not present REIT MoS with the same "margin of safety vs. intrinsic value" language the non-REIT MoS pillar uses — flagged for those later phases, not resolved here.
9. **No new REST endpoint.** RM2 is entirely a persistence/computation phase consumed by the existing `GET /api/v1/securities/{symbol}/score` and `GET /api/v1/securities/{symbol}/ratios` endpoints (already reading `RatioSnapshot`) — RM3 decides what to expose on the screener/security-detail response DTOs from the fields RM2 persists.
10. **`interestExpense` is confirmed live** (re-verified against `O`/`PLD`/`SPG`'s real `/income-statement` payload during implementation, not assumed) — present and populated on all three, so EBITDA interest coverage is computed (`ebitda / interestExpense`), not left `INSUFFICIENT_DATA` as `plan.md`'s original contingency anticipated. `capitalExpenditure` was already a trusted, pre-existing `FmpCashFlowEntry` field; it is ingested (`FundamentalSnapshot.capitalExpenditureHistory`) for completeness/future cross-check use, but AFFO's recurring-capex figure actually reuses the existing `maintenanceCapexDepreciationRatio` config value applied to D&A (`OwnerEarningsCalculator.estimateMaintenanceCapex`), per the definition doc's explicit instruction — `capitalExpenditure` itself is not read by `SectorMetricService`.
11. **`PipelineRunService` needed no separate ordering fix.** Investigated per `plan.md` Group 5.2's own instruction to "confirm its own price/ratio ingestion ordering first" — `PipelineRunService.run()` delegates seeding to `SeedService.seedTickers()` → `SeedTickerService.seedOne()`, so Decision 3's fix (calling `sectorMetricService.compute()` before `valueScoreService.compute()` inside `seedOne()`) already covers `PipelineRunService`'s downstream `valueScoreService.compute()` call — its sector metrics are already persisted by the time that second, redundant score computation runs.

## Data Shapes

```java
// RatioSnapshot — 7 new nullable columns (V29), null for every non-REIT and Yahoo-fallback row
BigDecimal ffoPerShare;             // (netIncome + D&A) / sharesOutstanding
BigDecimal affoPerShare;            // ffoPerShare − recurring-capex-per-share
BigDecimal priceToFfo;              // impliedPrice / ffoPerShare
BigDecimal priceToAffo;             // impliedPrice / affoPerShare
BigDecimal netDebtToEbitda;         // (totalDebt − cash) / ebitda
BigDecimal interestCoverageEbitda;  // ebitda / interestExpense
BigDecimal affoPayoutRatio;         // (payoutRatio × eps) / affoPerShare

// ValuationBandResult — one new metric value alongside PE/PB/EV_EBITDA/DIVIDEND_YIELD
metric = "P_FFO"   // same ValuationBandPosition enum, same percentile-band shape, higherIsCheap=false
```

- Implied Cap Rate and estimated NAV per share (out of scope per RM1's confirmed NOI-unavailability finding, Fallback C).
- `ThesisInput`/`thesis-input.schema.json` changes and prompt-content review for REIT awareness (`RM4`).
- A separate `financial`- or `utility`-sector `SectorMetricProfile` (explicitly deferred by the definition doc's own §2).
- Wiring `SectorMetricService` into `BulkRatiosSyncJob`/`BulkFundamentalsSyncJob` (existing seed-time-only precedent for derived-analytics services, unchanged).
- Retiring the RM0 GAAP-metric caveat (that happens in RM3, once a computed sector-aware replacement is actually displayed alongside it — RM2 computes but does not yet surface).
- Any frontend change.

## Compatibility and Risks

- **`interestExpense` availability was confirmed live during implementation** (re-verified against `O`/`PLD`/`SPG`'s real `/income-statement` payload, per Decision 10) — resolved from `plan.md`'s original "confirm before writing the formula" open item to a wired, tested field. Not a residual risk.
- **Net Debt/EBITDA reads more conservatively (higher) than a REIT's own company-reported adjusted leverage ratio**, confirmed with a real-data spot check on `O` during this phase: computed Net Debt/EBITDA ≈ 9.1× (raw, unadjusted `ebitda`) vs. Realty Income's own reported EBITDAre-based leverage of roughly 5.5×. This is a direct, expected consequence of RM1's confirmed finding that gains/losses on real-estate sales are not isolable from FMP's fundamentals data (`specs/sector-aware-valuation-metrics.md` §5) — raw EBITDA is not the NAREIT-adjusted EBITDAre the market actually benchmarks REIT leverage against. **Practical effect:** the Safety pillar's REIT thresholds (Decision 7, first-pass calibration) may currently score a conservatively-levered, investment-grade REIT like `O` more harshly than its real credit profile warrants. Flagged here as a concrete, evidenced finding (not a hypothetical) for whoever next recalibrates `SectorMetricProperties` against real NAREIT/sector benchmark data.
- **The AFFO recurring-capex heuristic (D&A × 0.70) is a poor fit for net-lease REITs specifically**, also confirmed with a real-data spot check on `O`: the computed AFFO/share (~$1.99, using the blanket 0.70 ratio) is materially lower than Realty Income's own reported AFFO/share (~$4.22 for FY2025), because net-lease REITs typically push property-level maintenance capex onto tenants under NNN leases, so their true recurring capex is far below 70% of D&A. The 0.70 ratio is reused unchanged from the DCF engine's owner-earnings calculation per the definition doc's explicit instruction (Decision 5) — this is a known, disclosed limitation of that reuse for this specific REIT sub-type, not a computation bug. AFFO-derived pillars (Dividend's AFFO payout ratio, the AFFO/FFO relationship generally) should be read with this in mind until a REIT-specific recurring-capex heuristic is scoped as a later, explicit decision.
- **The Group 4/5/7 calibration decisions (Quality formula, Safety/Dividend thresholds) are first-pass and provisional**, explicitly flagged in Decisions 6–7 — a future phase revisiting them against real NAREIT/sector benchmark data is expected, not a sign this phase under-delivered. The two findings above are concrete evidence *why* that recalibration matters, not just a theoretical caveat.
- **The implied-price derivation (`peRatio × eps`) compounds any error already present in the provider's own historical `peRatio`** — accepted, since it is still more accurate than either fabricating a price or omitting historical P/FFO bands entirely, and it is transparently documented rather than presented as an observed market price. A real-data spot check on `O` (implied P/FFO ≈ 15.7× against FY2025 figures) fell within Realty Income's typical historically-observed P/FFO range, a reasonable plausibility check though not a precise reconciliation against the company's own reported figure.
- **`ValueScoreService`'s constructor signature changes** (new `SectorMetricProperties`/`ValuationHistoryService` dependencies) — every existing test/call site constructing it directly must be updated; a compile-time break, not a silent behavior change, so it will surface immediately in `mvn test` if missed.
- **`ValueScoreService.computeMosScoreReit` calls `ValuationHistoryService.compute()` live on every REIT score computation**, which deletes and re-persists all five `ValuationBandResult` rows for that security (`ValuationHistoryService.compute`'s existing delete-then-saveAll behavior, unchanged by RM2). This is consistent with `MoatController`/`SecurityReviewService`'s existing on-demand-recompute usage of the same method — not a new class of behavior — but RM2 adds a third caller, increasing how often that churn happens for REIT securities specifically. Not a correctness issue; flagged as a minor, disclosed perf/DB-churn characteristic.
