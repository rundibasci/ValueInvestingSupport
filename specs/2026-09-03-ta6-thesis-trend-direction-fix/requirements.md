# TA6 — AI Thesis Trend-Direction Correctness Fix

## Context

RM4 (merged 2026-09-02) fixed `ThesisInputBuilder.deriveNetDebtToEbitda`'s indexing bug (it read `ebitdaHistory.get(size() - 1)` as "latest," silently picking the *oldest* year in a multi-year, newest-first history) and, while root-causing it against real `fundamental_snapshot` data, found a second, larger-scope, related bug it deliberately left unfixed: `ThesisInputBuilder.classifyTrend` (used for `revenueTrend`/`earningsTrend`/`freeCashFlowTrend`, all three fed to every AI Investment Thesis regardless of sector) makes the opposite array-direction assumption from every other reader of these same history lists.

Confirmed against real code this session, not assumed from RM4's prose alone:
- `FmpAdapter.toFundamentalSnapshot` builds `revenueHistory`/`netIncomeHistory`/`fcfHistory` (and every other `*History` list) from FMP's own newest-first statement ordering — `income.get(0)`/`balance.get(0)` are read as "current/TTM" for `epsTtm`/`totalDebt`/`cash`/`shares` in that same method (`backend/src/main/java/it/mazzoni/vis/marketdata/fmp/FmpAdapter.java:40-48`).
- `DemoAnalysisService` independently reads `fcfHistory.get(0)` as the TTM figure and `fcfHistory.get(fcfHistory.size() - 1)` as the oldest, for its own growth estimate (`backend/src/main/java/it/mazzoni/vis/demo/DemoAnalysisService.java:90-108`).
- RM4's own (already-merged) `deriveNetDebtToEbitda` fix reads `ebitdaHistory.get(0)` as "latest," with its Javadoc citing both of the above as independent confirmation of the newest-first convention (`backend/src/main/java/it/mazzoni/vis/thesis/ThesisInputBuilder.java:179-193`).
- `classifyTrend` (`backend/src/main/java/it/mazzoni/vis/thesis/ThesisInputBuilder.java:147-177`) does the opposite: it iterates `for (int i = 1; i < history.size(); i++)`, treating `history.get(0)` as the *oldest* point and `history.get(history.size() - 1)` as the *newest*, then reports `periodChanges.get(periodChanges.size() - 1)` — the change between the two oldest comparable points in a newest-first array — as "latest."

Net effect: for any security with 3+ years of history, `revenueTrend`, `earningsTrend`, and `freeCashFlowTrend` are plausibly classified from the oldest comparable year-over-year change in the fetched window, not the most recent one — for every AI thesis generated since TA4 shipped (2026-08-28). This is a correctness defect in a feature whose entire value proposition (mission.md Principle 15) is "reason from evidence, don't invent" — the evidence itself has plausibly been mislabeled by direction. Full root-cause writeup: `specs/2026-09-02-rm4-ai-thesis-propagation/validation.md` → Known Risks (Correction 2).

This phase is that follow-up, as the roadmap itself calls for ("Strongly recommended as the next phase after RM4, verified against real multi-year data for several tickers — not just synthetic 2-element test fixtures, which cannot expose a direction bug").

| Rewriting `ThesisInputBuilderTest`'s existing `classifyTrend_*` fixtures to newest-first order, with an explicit comment on the convention (the current fixtures, e.g. `series("100", "120")` read as oldest-first, silently encode the same inverted assumption the production code has — a same-order rewrite would keep passing against either a correct or a buggy implementation and prove nothing) | Any change to `MoatAssessmentService.classifyTrend` — a different method, same name, unrelated: it classifies a *slope* computed via linear regression over an ROIC series, not a period-over-period percentage change over a raw history list, and never assumed a direction on a shared `*History` convention. Confirmed by inspection this session |
| Live verification against real multi-year FMP history for at least one real ticker where the fetched window's oldest and newest comparable period-over-period changes point in genuinely different directions (so the bug, if still present, is observable — a monotonic series can't expose a direction bug) | Backfilling `revenueTrend`/`earningsTrend`/`freeCashFlowTrend` into historical `InvestmentThesisResult` rows already generated before this phase — same posture RM4 took for `netDebtToEbitda`; only new generations after merge see the corrected value |
| Updating `classifyTrend`'s own Javadoc to state the newest-first convention explicitly (today's Javadoc, lines 141-146, describes the threshold bands but says nothing about array direction — the exact gap that let this bug ship unnoticed since TA4) | Any prompt (`system-prompt-v3.txt`), schema, or `evidenceFields` change — `revenueTrend`/`earningsTrend`/`freeCashFlowTrend` are already-citable evidence fields (TA4) with unchanged names and unchanged `Trend` enum values; only the classification logic underneath is being corrected, not the field's declared shape or prompt-facing description |

## Decisions

1. **Fix by reversing the list to chronological order once, at the top of the method, then reusing the existing period-change/threshold logic unchanged.** `classifyTrend` receives `history` newest-first; the simplest, lowest-risk fix is `List<BigDecimal> chronological = new ArrayList<>(history); Collections.reverse(chronological);` immediately after the size guard, then every line below operates on `chronological` exactly as it does today on `history`. This was chosen over rewriting the loop to walk `history` in reverse index order (functionally equivalent, but touches more lines and is more error-prone to get right on the first pass — an off-by-one in a reversed-index loop is exactly the class of bug this phase exists to remove, not risk reintroducing in a different form) and over changing what "latest" means downstream (rejected — every other consumer of `periodChanges`/the volatility check keeps working unmodified against a chronological list, which is the array orientation this logic was actually written to assume).
2. **The existing unit test fixtures are rewritten to be genuinely newest-first, not just re-labeled.** `classifyTrend_stronglyGrowing_onLargeIncrease`'s current `series("100", "120")` will become `series("120", "100")` (latest 120, prior 100 — still a +20% increase, still `STRONGLY_GROWING`, but now the input order actually matches production data) rather than merely renaming the test or adding a comment to the old order. Confirmed by inspection this session: today's fixtures happen to pass under *either* a correct or an inverted implementation for the simple growing/declining/stable cases (a 2-element series has no "which end is latest" ambiguity for the reader unless the *values themselves* are also checked against a known direction) — but they document the wrong convention for a future reader, which is precisely how this bug went unnoticed through TA4/RM4's own review. The volatile-case fixture (`series("100", "200", "210")`, 3 elements) is reordered to `series("210", "200", "100")` so its own comment ("the huge first swing marks this volatile even though the latest period alone would read as merely 'growing'") stays true under the corrected convention.
3. **Live verification uses a real, multi-year ticker whose oldest and newest fetched-window period-over-period changes point in different directions**, per the roadmap's own explicit recommendation — a monotonic series (steadily growing or steadily declining every year) cannot distinguish a fixed implementation from the current buggy one, since both would report the same overall direction by coincidence. The ticker and specific field are chosen from real fetched data during implementation (confirmed live, not picked in advance from memory of past figures) rather than named speculatively here.
4. **`MoatAssessmentService.classifyTrend` is confirmed out of scope, not merely assumed unrelated**, per this project's own "verify against real code" discipline: it takes a `BigDecimal slope` (a linear-regression coefficient already computed elsewhere, `backend/src/main/java/it/mazzoni/vis/moat/MoatAssessmentService.java:82`) and classifies its sign/magnitude — it never indexes into a `*History` list itself, so it carries no array-direction assumption to invert.
5. **No backfill of previously generated `InvestmentThesisResult` rows.** Matches RM4's own accepted posture for `netDebtToEbitda` (`specs/2026-09-02-rm4-ai-thesis-propagation/requirements.md` had no backfill scope either) — a live user can regenerate a thesis on demand at any time, and this platform never auto-regenerates a persisted thesis, so a backfill would be a separate, explicit data-migration decision, not implied by a code fix.

## Data Shapes

No new or changed field, schema, enum value, or API shape. `Trend` (`STRONGLY_GROWING`, `GROWING`, `STABLE`, `DECLINING`, `STRONGLY_DECLINING`, `VOLATILE`, `NOT_AVAILABLE`), `ThesisInput.revenueTrend`/`earningsTrend`/`freeCashFlowTrend`, and the `evidenceFields` enum entries for all three are unchanged — this phase corrects which historical period `classifyTrend` reads as "latest," not any type or contract.

## Out of Scope

- Recalibrating `STRONG_THRESHOLD` (15%), `MILD_THRESHOLD` (3%), or `VOLATILITY_THRESHOLD` (50%).
- `MoatAssessmentService.classifyTrend` (different method, unrelated algorithm, confirmed by inspection — Decision 4).
- Backfilling historical `InvestmentThesisResult.input_snapshot` rows generated before this phase (Decision 5).
- Any prompt, schema, or `evidenceFields`/`EvidenceField` enum change — TA4 already made these three fields citable; only their underlying classification is being corrected.
- Any frontend change — confirmed no UI surface reads a raw `Trend` value.
- A prompt-quality evaluation harness for how the AI reasons about corrected trend values — same posture RM4 took for its own prompt-content review; out of scope for a backend classification-logic fix with no prompt change attached.
