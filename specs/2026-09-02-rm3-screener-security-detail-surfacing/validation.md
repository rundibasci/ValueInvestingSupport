## Corrections Made During Implementation (honest account)

Per this project's own "verify against real code, not spec text" discipline (RM2/TA4/TA5 precedent):

1. **`SectorMetricResponse`'s availability field reuses the existing `AvailabilityResponse`/`AvailabilityStatus` type**, not the hand-rolled `availabilityStatus`/`availabilityMessage` string pair `plan.md`'s sketch proposed. `AvailabilityStatus` has no `INSUFFICIENT_DATA` value; `MISSING_INTERNAL_COMPUTATION` is the correct existing value for "a REIT security whose sector metrics haven't been computed yet." Found by checking the type before assuming, per the plan's own instruction.
2. **A param-position bug was caught and fixed during test-writing, not left in**: an early draft of `search_maxNetDebtToEbitda_excludesHighlyLeveredReits` placed its threshold value in the `maxPriceToFfo` constructor slot instead of `maxNetDebtToEbitda` (both are adjacent `BigDecimal` parameters), which silently filtered out every REIT row including the one the test expected to survive. Caught by the test actually failing (empty result instead of `["PLD"]`), not by inspection — the test did its job.
3. **The FMP-key environment gap during manual verification** (Manual Verification step 1) was a session setup mistake, not a code defect — recorded above for completeness since it delayed live verification, not because it reflects on RM3 itself.

## Known Risks (carried forward or introduced by this phase)

- **RM2's own disclosed calibration risks (AFFO understatement for net-lease REITs, Net Debt/EBITDA reading more conservatively than company-reported EBITDAre-based leverage) are now directly visible to end users for the first time**, since RM3 is the first phase that renders these numbers in the product rather than only in a `psql` inspection or unit test. This is a feature of transparency (Design Principle 2 — every displayed formula also documents its known limitation via the formula-string constants), not a new defect this phase introduces — but it does mean a real user can now notice `O`'s Net Debt/EBITDA reading ~9.1× and its Safety-pillar score being 0.0 (confirmed live again this session, consistent with RM2's own finding), and ask why, before a future recalibration phase addresses it.
- **The three new screener filters silently scope to REIT-only results** (Decision 2, confirmed live) — disclosed via UI copy, but still a real UX rough edge if a user sets one of these filters expecting it to also narrow (rather than eliminate) non-REIT results. Not fixed in this phase; flagged for a possible future UX pass if it proves confusing in practice.
- **`SecurityDetailPage.tsx` remains without any REIT caveat or sector-metric surfacing** (Decision 9) — a known, pre-existing gap carried forward from RM0, not introduced by RM3. A user who only visits this legacy page (rather than the in-depth Review page) still sees unflagged GAAP metrics for a REIT security.
- **The screener's per-row `sectorMetricCaveat` (RM0) is unchanged** (Decision 8) — it still fires identically for REIT and utility rows even though REIT rows now have a computed replacement visible elsewhere in the same row. A future phase could reasonably narrow this once a clearer "next to" relationship is defined for the screener's row layout specifically.
- **No browser-rendered visual verification of the new UI was performed this session** (Manual Verification, final paragraph) — the frontend types and rendering logic were verified by code inspection and against live API payloads, and `npm run build` passed, but no screenshot or click-through evidence exists. A future session with a running `npm run dev` + browser pass would close this gap.
- **The screener's live `O` P/FFO (15.6929) differs from RM2's own validation snapshot (15.6442)** — expected drift from the TTM row's implied price tracking the current live `PriceQuote`, not a computation regression; documented here so a future reader doesn't mistake it for one.
