# RM5 — REIT-Aware Composite Fair Value & Margin of Safety

## Context

**Found by direct user observation of a live AI thesis on staging (2026-09-03), root-caused against real code, not assumed.** RM4's live-verified thesis for `O` (a REIT) leads its bear case with *"trading significantly above its calculated intrinsic value with a negative margin of safety"* — but `ThesisInputBuilder.build()` reads `marketPrice`/`intrinsicValue`/`marginOfSafetyPercent` straight from `ValuationResult` (`valuation.map(ValuationResult::getCurrentPrice/getCompositeFairValue/getMarginOfSafety)`), and `ValuationService.calculate()` ([backend/src/main/java/it/mazzoni/vis/valuation/ValuationService.java:79-107](backend/src/main/java/it/mazzoni/vis/valuation/ValuationService.java#L79)) has **zero `SectorClassifier.isReit` branching anywhere in the file** — `compositeFairValue` is unconditionally a weighted blend of DCF (free cash flow, GAAP), Graham Number (EPS, GAAP), and DDM, for every sector including REITs. This is the exact same GAAP-earnings distortion class the whole M28/Group RM effort exists to fix — just never actually fixed for this specific, highest-visibility output.

**This is not a new discovery about the domain — it's a gap in the original design doc's own follow-through.** `specs/sector-aware-valuation-metrics.md`'s own distortion table (line 17) lists **"MoS | Composite fair value built on DCF/Graham Number, both anchored to EPS"** as a row alongside P/E, ROE/ROIC, and Debt/Equity — the doc's authors already knew `ValuationResult.marginOfSafety` was in-scope for the same distortion. But the doc's §4.3 (line 96) explains why a *true* REIT intrinsic value was never attempted: *"rather than against a DCF-derived intrinsic value, since REIT DCF requires property-level cash flow modeling this platform does not attempt"* — the same data-availability wall RM1 later confirmed empirically for Implied Cap Rate and NAV per share (Fallback C, permanently out of scope). The workaround chosen instead — a **P/FFO percentile-vs-own-history band** — solved the *Value Score's MoS pillar* (a 0-100 relative-cheapness score, which a percentile position answers perfectly well) but was **never connected back** to `ValuationResult.compositeFairValue`/`marginOfSafety` (a literal "%-below-intrinsic-value" figure, which a percentile position cannot answer without a further design decision — converting a relative percentile into an absolute implied fair price). RM2's own `plan.md` (Group 4, item 2) flagged this exact gap in an implementation comment — *"a real behavioral difference the AI thesis / UI must not blur (RM3/RM4 concern, flagged here for continuity)"* — but it was never elevated to a roadmap-level Known Risk (unlike TA6's `classifyTrend` bug), so it was never re-surfaced when RM4 actually built the AI Thesis integration on top of the still-untouched field, or by RM0/RM3's own screener/security-detail GAAP-metric caveat, which lists only **"P/E, ROE/ROIC, and Debt/Equity"** ([SectorClassifier.java:24](backend/src/main/java/it/mazzoni/vis/common/SectorClassifier.java#L24), [SecurityReviewService.java:623](backend/src/main/java/it/mazzoni/vis/security/SecurityReviewService.java#L623)) — margin of safety/fair value was never in that caveat's scope either, even though the original table said it should be.

**What this phase does, per explicit user decision (2026-09-03):** compute a genuine, REIT-appropriate substitute fair value from FFO/AFFO multiples — not a property-level DCF (still confirmed infeasible, RM1's finding stands) — and make it **the** `compositeFairValue`/`marginOfSafety` for REIT-classified securities, so screener, security-detail, and the AI thesis all inherit the fix from the one place they already share (`ValuationResult`), with no separate code change needed in any of the three consumers.

## Decisions

1. **The substitute fair value is AFFO-based (P/AFFO), not FFO-based (P/FFO), even though only a `P_FFO` band exists today.** AFFO nets out recurring/maintenance capital expenditures and is this project's own documented "true distributable cash" REIT metric (`specs/sector-aware-valuation-metrics.md` §4.2) — a materially better proxy for what an intrinsic-value estimate should represent than FFO, which still includes capex a REIT must spend just to maintain its existing portfolio. This means adding a new `P_AFFO` band (Decision 2) rather than reusing the existing `P_FFO` one, even though it would have been zero-additional-code to reuse what RM2 already built.
2. **A new `P_AFFO` valuation band is added, mirroring `P_FFO` exactly** (`ValuationHistoryService.compute`, one new line: `band(security, resultDate, "P_AFFO", annuals, RatioSnapshot::getPriceToAffo, false)`). This is the same additive, zero-non-REIT-impact mechanism RM2 already proved for `P_FFO` (a non-REIT's `priceToAffo` is always `null`, so the band resolves to `INSUFFICIENT_DATA` with no branching needed) — not a new pattern, a proven one applied to a second field.
3. **`compositeFairValue`/`marginOfSafety` are *replaced*, not supplemented, for REIT securities** — a REIT's headline "Fair Value"/"Margin of Safety" (shown on the screener, security-detail page, and now correctly informing the AI thesis) becomes the AFFO-based figure outright, not a second parallel number the user has to reconcile against the old GAAP one. This is the more invasive of two options considered (the alternative — a separate `reitFairValue`/`reitMarginOfSafety` pair left alongside the unchanged GAAP ones — was rejected) because a parallel field would require every consumer (screener column, security-detail card, `ThesisInputBuilder`) to be individually taught which figure to prefer, reintroducing exactly the "AI thesis / UI must not blur" risk RM2's own plan.md flagged — replacing the one shared field fixes all three consumers at once, which is the whole reason this phase is worth doing this way.
4. **`dcfFairValue`, `grahamNumber`, `ddmFairValue`, `epvFairValue`, and `ownerEarnings` keep being computed and persisted for REIT securities, unchanged.** They remain individually informative (a REIT's Graham Number is still a real, if GAAP-distorted, number worth showing next to a clear caveat) and this phase does not touch `runGraham`/`runDcf`/`runDdm`/`runEpv`/`computeOwnerEarnings` at all — only `compositeFairValue`'s composition and `marginOfSafety`'s input change for the REIT branch. Removing the sub-fields would be a larger, separate UI/API-contract decision this phase does not make.
5. **No silent fallback when AFFO data is insufficient.** A REIT whose `P_AFFO` band is `INSUFFICIENT_DATA` (fresh seed, or fewer than 3 annual `RatioSnapshot` rows with a computed `priceToAffo`) or whose latest `RatioSnapshot.affoPerShare` is `null` gets `compositeFairValue = null`, `marginOfSafety = null`, `affoFairValue = null` for that run — not a reversion to the DCF/Graham/DDM blend. This matches Design Principle 12 (`INSUFFICIENT_DATA` over a fabricated number) and is the actual point of this phase: a `null` MoS the UI/AI honestly labels as unavailable is strictly better than a confidently wrong GAAP-based one masquerading as sector-neutral.
6. **`ThesisInputBuilder` requires no code change.** Verified by inspection (Decision confirmed, re-verified in this phase's own live validation): it already reads `ValuationResult.getCurrentPrice()`/`getCompositeFairValue()`/`getMarginOfSafety()` — the exact three fields this phase fixes at the source. This is the intended payoff of fixing the shared entity rather than adding thesis-specific logic, matching this phase's own Decision 3 rationale.
7. **RM0/RM3's GAAP-metric caveat gets one added sentence, not a rewrite.** `SectorClassifier.REIT_UTILITY_METRIC_CAVEAT` and `SecurityReviewService.buildNotes`'s REIT-specific note both currently scope their warning to "P/E, ROE/ROIC, and Debt/Equity" only — technically correct (they never claimed to cover margin of safety), but liable to be misread by a user seeing an uncaveated MoS number right next to a GAAP-metric warning. After this phase, a REIT's MoS is *actually* AFFO-based and correct, so the fix is to say so explicitly (e.g. "Margin of Safety and Fair Value are computed from an AFFO-based multiple for this sector, not the GAAP-based DCF/Graham/DDM composite used elsewhere"), not to extend the warning to cover a number that is no longer distorted.
8. **Utilities are explicitly out of scope**, gated by `SectorClassifier.isReit` (not `isReitOrUtility`) — same boundary RM2 already drew and this project has deferred since (`specs/sector-aware-valuation-metrics.md` §10, open question 4: "a future Financial/Utility metric redefinition doesn't require a second refactor" — that refactor still hasn't happened, and this phase doesn't attempt it).

## Out of Scope

- A true property-level REIT DCF/cap-rate/NAV-based intrinsic value — confirmed infeasible by RM1's own FMP field-availability finding; unchanged.
- Utility securities — `isReitOrUtility`'s utility half is untouched; utilities keep the GAAP composite and RM0's original, unmodified caveat.
- Recalibrating any RM2 `SectorMetricProperties` threshold or the AFFO recurring-capex heuristic's already-disclosed calibration risk.
- Removing, hiding, or restructuring `dcfFairValue`/`grahamNumber`/`ddmFairValue`/`epvFairValue`/`ownerEarnings` for REIT securities — all remain computed and persisted exactly as before.
- Any change to `ThesisInputBuilder`, the evidence-field parity chain, or `system-prompt-v3.txt` — the fix is entirely upstream of the thesis layer.
- Backfilling historical `ValuationResult` rows generated before this phase's merge.
- A dedicated evaluation harness proving the AI reasons correctly about the now-corrected `marginOfSafetyPercent` for a REIT — out of scope the same way RM4 scoped its own prompt-content review (one live smoke-test reading, not an automated benchmark).
